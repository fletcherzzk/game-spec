# Bughouse Chess - Phase 1

## Features

Four players join one shared match from separate browsers. Two boards show standard
starting positions with all pieces and coordinate labels. Team 1 is A White + B Black;
Team 2 is A Black + B White. Both boards start when all four seats are connected.

Pawns can move one square forward, or two from their starting rank if the path is
empty. Each board tracks turns independently. All players start with three minutes
and receive two seconds after each valid move. A timeout ends the entire match;
exactly simultaneous opposing flags draw. Four rematch votes reset a finished match.

Captures, transfers, drops, reserves, other piece movements, check, checkmate,
promotion, castling, and en passant are outside Phase 1. See [spec.md](spec.md).

## Architecture

```text
GitHub Pages                              Render
frontend/index.html                       backend/app.py
frontend/assets/*   -- Socket.IO moves --> backend/game.py
frontend/config.js  <-- state snapshots -- authoritative game and clocks
```

The frontend is plain HTML/CSS/JavaScript. It has no Flask or Jinja dependencies.
Relative asset paths support GitHub Pages project URLs with a repository subpath.
Flask disables its static handler and does not serve HTML or frontend assets.
The backend exposes only Socket.IO at `/socket.io/` and a JSON `GET /health` endpoint.
The backend root `/` returns 404 intentionally.

```text
frontend/                     Publish this folder to GitHub Pages
  index.html
  config.js                   Public backend URL
  assets/
    app.js
    style.css
    vendor/socket.io.min.js
backend/                      Render service root directory
  app.py
  game.py
  requirements.txt
  tests/
render.yaml                   Render Blueprint
.github/workflows/pages.yml    GitHub Pages deployment workflow
```

The server validates every move and serializes actions under a lock. Python's
monotonic clock owns timing. Snapshots broadcast every 250 ms and after actions.
Clients interpolate countdown displays between snapshots, but only the server
awards increments and decides timeouts. Both boards remain visible to every player.

## Local setup

Requires Python 3.10 or newer. From the repository root, run the backend:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe backend/app.py
```

In a **second terminal**, independently serve the frontend:

```powershell
.\.venv\Scripts\python.exe -m http.server 8000 --directory frontend
```

On macOS/Linux, create the environment with `python3 -m venv .venv`, and replace
`.\.venv\Scripts\python.exe` with `.venv/bin/python` in the remaining commands.

Open **http://localhost:8000**, not port 5000. Open four independently created tabs
or browser profiles, enter names, and join different seats. Click your pawn and a
highlighted destination to move. Additional browsers can spectate without joining.
Do not open the HTML through a `file://` URL.

The checked-in `frontend/config.js` uses `http://localhost:5000` when the page is
opened on localhost or 127.0.0.1. For LAN testing, change `backendUrl` to the backend
computer's URL (for example `http://192.168.1.10:5000`) and set the backend environment
variable `FRONTEND_ORIGINS` to the frontend origin (`http://192.168.1.10:8000`).
Restart the backend and open that frontend URL on all devices.

## Render backend deployment

1. Push this repository to GitHub.
2. In Render, create a **Blueprint** from the repository. The root `render.yaml`
   configures the Python web service with `backend` as its root directory.
3. Supply `FRONTEND_ORIGINS` when prompted. For a Pages URL such as
   `https://YOUR-USER.github.io/YOUR-REPO/`, enter **`https://YOUR-USER.github.io`**.
   Include scheme and hostname, without the repository path. Use comma-separated
   values if you also have a custom frontend domain.
4. Deploy and copy the HTTPS service origin, such as `https://YOUR-SERVICE.onrender.com`.
5. Visit `https://YOUR-SERVICE.onrender.com/health` and confirm `"status":"ok"`.

For manual service creation, use:

| Setting | Value |
| --- | --- |
| Runtime | Python |
| Root directory | `backend` |
| Build command | `pip install -r requirements.txt` |
| Start command | `gunicorn --bind 0.0.0.0:$PORT --workers 1 --threads 100 --timeout 120 app:app` |
| Health check | `/health` |
| Instances | `1` |
| `FRONTEND_ORIGINS` | GitHub Pages origin, without a path |
| `SECRET_KEY` | Random secret; generated by the Blueprint |
| `PYTHON_VERSION` | `3.13.7` |

Keep **one worker and one instance**. The single match lives in process memory;
multiple workers or instances would create separate games. Restarting or redeploying
the backend resets the match. Gunicorn runs on Render's Linux runtime; local Windows
development uses `python backend/app.py`.

The production command follows the
[Flask-SocketIO deployment guide](https://flask-socketio.readthedocs.io/en/latest/deployment.html).
Blueprint fields follow [Render's reference](https://render.com/docs/blueprint-spec).

## GitHub Pages frontend deployment

1. In GitHub, open **Settings > Secrets and variables > Actions > Variables**.
2. Add a repository variable **`BACKEND_URL`**, for example
   `https://YOUR-SERVICE.onrender.com`. Use the HTTPS origin without a path.
   This URL is public configuration, not a secret.
3. Open **Settings > Pages**, and select **GitHub Actions** as the build source.
4. Under **Actions**, manually run **Deploy frontend to GitHub Pages**, or push a
   frontend change to `main`. Change the workflow branch filter if your default
   branch has another name.
5. Open the workflow's Pages URL. Confirm Render's `FRONTEND_ORIGINS` matches
   its origin exactly.

The workflow validates `BACKEND_URL`, writes it into `config.js` in the deployment
artifact, and publishes **only `frontend/`**. Backend source is not in that artifact.
Missing or invalid backend URLs fail the workflow with setup guidance. After
changing the repository variable, rerun the workflow to update the deployed site.

For manual static hosting, set `frontend/config.js` to:

```javascript
window.BUGHOUSE_CONFIG = {
  backendUrl: 'https://YOUR-SERVICE.onrender.com'
};
```

Upload the contents of `frontend/`. The checked-in configuration deliberately has
no production backend default; missing configuration shows a setup message.
The workflow follows GitHub's
[custom Pages workflow documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Configuration

| Location | Setting | Purpose |
| --- | --- | --- |
| GitHub repository variable | `BACKEND_URL` | Render HTTPS origin injected during Pages deployment |
| Frontend `config.js` | `backendUrl` | Runtime Socket.IO server origin |
| Backend environment | `FRONTEND_ORIGINS` | Comma-separated allowed frontend origins |
| Backend environment | `SECRET_KEY` | Flask secret; never include in frontend files |
| Backend environment | `PORT` | Render supplies this; local default is 5000 |

Without `FRONTEND_ORIGINS`, local origins `http://localhost:8000` and
`http://127.0.0.1:8000` are allowed. Wildcards and origins with paths are rejected.
The browser client sends no cross-origin cookies. CORS checks browser origins;
it does not provide account authentication.

Seat reconnection uses a private server-issued token in tab-scoped `sessionStorage`.
Tokens are never broadcast in public snapshots. Reloading the same tab restores its
seat. During a match, disconnected seats remain reserved and clocks continue.
Lobby seats are released on disconnect. Duplicating a tab may copy its token;
use independently opened tabs or separate profiles for different players.

## Tests and deployment checks

From the repository root:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s backend/tests -t backend -v
node --check frontend/assets/app.js
node --check frontend/config.js
```

Tests cover pawn movement, blocked paths, independent turns, server clocks and
increments, timeout ordering, reconnect ownership, rematches, malformed events,
synchronized snapshots to four players and a spectator, allowed/rejected
cross-origin handshakes, and the absence of frontend routes in Flask.

After deployment, open the Pages URL in four browsers, join all seats, move a
white pawn on each board, and check that both moves and all clocks synchronize.
Reload a seated tab to check reconnection.

## Troubleshooting

- **Render `/` is 404:** expected; open the Pages frontend and use `/health` for the backend.
- **Backend URL required:** set `BACKEND_URL` and rerun Pages deployment, or edit `config.js`.
- **Backend unavailable / origin rejected:** confirm the Render HTTPS URL and health check,
  and match `FRONTEND_ORIGINS` to the Pages origin without its repository path.
  A cold-starting backend may take time to respond.
- **Assets return 404:** publish `frontend/` as the artifact root and preserve its subfolders.
- **Players see different games:** use one worker, one instance, and the same backend URL.
- **Match disappears:** backend state is in memory and resets when the process restarts.

Deployment configuration is included. Connecting hosting accounts, setting actual
URLs, and running the hosting workflows remain deployment steps.
